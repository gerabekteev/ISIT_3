# Лабораторная работа №1 — Задачи

> Источник требований: методичка «Архитектурное моделирование программных систем на основе модели C4» (МГТУ СТАНКИН, 2026, в2), раздел 1.1 и раздел 5 (пример). Командные интеграционные требования — из Семинара 1, слайды 16–17 (см. `../теория/`).
>
> ⚠️ О нумерации: в методичке **ЛР1 = контекст (L1) + контейнеры (L2)**. На слайдах лекции/семинара контекст и контейнеры названы ЛР1 и ЛР2 по отдельности. Требования к самим диаграммам идентичны; сдавать следует обе диаграммы в рамках ЛР1 по методичке.
>
> Все диаграммы строятся **строго по теме своего курсового проекта**. Кейс «Умная парковка» из методички — демонстрационный пример, выполнять его нельзя.

## Общая цель

Научиться очерчивать границы проектируемой системы и раскрывать первый-второй уровни абстракции C4 Model: показать систему как «чёрный ящик» в окружении пользователей и внешних систем (L1), затем декомпозировать её на независимо развертываемые контейнеры с фиксированным технологическим стеком (L2).

Архитектура описывается как код (Diagrams-as-Code): каждый файл — `.puml` на базе библиотеки C4-PlantUML.

## Задача 1. Диаграмма системного контекста (System Context, L1)

**Что делаем:** первый уровень C4 — система в её естественной среде, взгляд «с высоты птичьего полёта». Система — единый неделимый «чёрный ящик»; никакой внутренней структуры на этом уровне не показываем.

**Элементы диаграммы:**
- **Персоны (Person)** — пользовательские роли системы; у каждой — описание служебного назначения;
- **Центральный блок** — проектируемая система (`System_Boundary`/`System`), «чёрный ящик»;
- **Внешние системы (`System_Ext`)** — сторонние программные/аппаратные системы;
- **Связи (Rel)** — направленные стрелки с описанием передаваемых данных и протоколом.

**Требования методички:**
1. Очертить жёсткие внешние границы системы, представив её единым неделимым «чёрным ящиком».
2. Центральный блок + **не менее 3 различных пользовательских ролей (персон)**.
3. **Не менее 3 внешних программных или аппаратных систем**, находящихся вне зоны прямого контроля разработчиков.
4. Все связи строго направленные, с обязательным текстовым описанием передаваемых данных.

**Командные требования (если работаете в команде из 5 человек):**
- Тимлид проектирует общую глобальную диаграмму контекста (мастер-файл `main.puml`) и проводит интеграционное ревью.
- Каждый разработчик делает индивидуальную версию L1 с фокусом на окружение **своего контейнера** (например: какие внешние точки входа у мобильного приложения).
- Глобальная диаграмма должна суммарно содержать ≥ 5 акторов и ≥ 3 внешних систем; команда утверждает единый перечень внешних систем.
- Даже в команде **каждый сдаёт и защищает ЛР1 лично**; преподаватель опрашивает индивидуально по всем уровням C4.

**Пример структуры элементов** (кейс Smart Parking из методички — только как образец компоновки):
- Персоны: Водитель (ищет и оплачивает места), Оператор парковки (мониторит, администрирует тарифы);
- Система: Smart Parking System;
- Внешние системы: Банковский эквайринг, Сервис геолокации/Карты, IoT-датчики и шлагбаумы;
- Связи: Водитель → система («команды бронирования и оплаты», HTTPS); система → эквайринг («запрос на списание средств», REST API/HTTPS) и т.п.

## Задача 2. Диаграмма контейнеров (Container, L2)

**Что делаем:** «зум на один шаг» — декомпозиция центрального блока L1 на обособленные, независимо развертываемые исполняемые сущности. Контейнер в C4 — не Docker-контейнер, а приложение/хранилище, которое должно выполняться для работы системы.

**Требования методички:**
1. Декомпозиция центрального системного блока на контейнеры.
2. **Не менее 5 технологических контейнеров** — обязательно включить: мобильное приложение, веб-приложение, бэкенд-сервисы и хранилища данных.
3. Для **каждого** контейнера — конкретный технологический стек (языки, фреймворки, СУБД).
4. Для всех межсервисных связей — чётко указанные **сетевые протоколы** взаимодействия.

**Дополнительно (методичка, раздел 1.1.2):** сформировать **подробную таблицу описания каждого контейнера** — идёт в отчёт.

**Командные требования (интеграция):**
- Тимлид определяет глобальный техстек, структуру СУБД, распределение микросервисов, координирует протоколы (HTTPS, MQTT, SQL).
- Каждый разработчик проектирует схему контейнеров с фокусом на **свой выделенный узел**, аргументируя выбранный стек.
- Сетевой регламент на стыках зон ответственности: HTTPS/JSON для API, SQL/TCP для БД, MQTT/TCP для IoT; указывать инициатора сессии.

**Пример из методички** (5 контейнеров Smart Parking): Мобильное приложение (React Native), Панель администратора (React/TypeScript), API Gateway & Backend (Python/FastAPI), Реляционная БД (PostgreSQL), Контроллер парковки / IoT-сервис (Python/Asyncio). Связи: driver→mobile_app (HTTPS), mobile_app→api_gateway («запросы на бронь», HTTPS/JSON), api_gateway→database («чтение/запись», SQL), api_gateway→payment_gateway («проведение оплаты», HTTPS/REST).

## Шаблон puml (структура, не копировать дословно)

```plantuml
@startuml "Название системы - System Context"
!include https://raw.githubusercontent.com/plantuml-stdlib/C4-PlantUML/master/C4_Context.puml
LAYOUT_WITH_LEGEND()

title Диаграмма системного контекста ИС "<ваша тема>"

Person(user1, "Роль 1", "Что делает пользователь этой ролью")
Person(user2, "Роль 2", "...")
Person(user3, "Роль 3", "...")

System(target, "<Целевая система>", "Краткое назначение системы")
System_Ext(ext1, "Внешняя система 1", "Краткое описание")
System_Ext(ext2, "Внешняя система 2", "Краткое описание")
System_Ext(ext3, "Внешняя система 3", "Краткое описание")

Rel(user1, target, "Бизнес-действие", "HTTPS")
Rel(user2, target, "Бизнес-действие", "HTTPS")
Rel(target, ext1, "Какие данные передаются", "REST API/HTTPS")
@enduml
```

Для L2 подключается `C4_Container.puml`, элементы — `Container(...)`/`ContainerDb(...)` внутри `System_Boundary(...)`, второй аргумент макроса — технологический стек, у `Rel` третий аргумент — бизнес-описание, четвёртый — протокол.

## Артефакты сдачи (чеклист)

- [ ] `*.puml` диаграммы системного контекста (L1) — рендерится без ошибок;
- [ ] `*.puml` диаграммы контейнеров (L2) — рендерится без ошибок;
- [ ] PNG/SVG-изображения обеих диаграмм;
- [ ] Таблица описания каждого контейнера (название, назначение, стек, связи/протоколы);
- [ ] Отчёт по ЛР1: цель, описание элементов и связей обеих диаграмм (текстовая спецификация — как в методичке), выводы;
- [ ] Отчёт размещён в электронной образовательной среде (ЭОС);
- [ ] Готовность защитить лично: уметь объяснить каждый элемент, связь, выбор протокола и стека.

## Содержание отчёта (по образцу методички)

1. Титул/тема курсового проекта.
2. Назначение диаграммы L1: какие границы очерчены, почему.
3. Текстовая спецификация элементов L1 (каждая персона/система с описанием роли) и связей (кто → кому, что передаёт, по какому протоколу).
4. Назначение диаграммы L2: логика декомпозиции.
5. Таблица контейнеров: ID, название, тип, технологический стек, описание, основные связи.
6. Текстовая спецификация связей L2 с протоколами.
7. Выводы.

## Пошаговый план выполнения

1. Зафиксировать тему курсового проекта и список ролей пользователей (≥ 3) и внешних систем (≥ 3).
2. Установить/проверить инструменты (см. `02_ограничения_ЛР1.md`, раздел «Инструменты»).
3. Написать `context.puml` (L1) по шаблону, отрендерить, проверить чеклист требований.
4. Продумать декомпозицию: какие независимо развертываемые части образуют систему (≥ 5), какой стек у каждой.
5. Написать `containers.puml` (L2), для каждой связи указать протокол.
6. Составить таблицу контейнеров.
7. Собрать отчёт и загрузить в ЭОС.
8. (Команда) Передать нарезку для `main.puml` Тимлиду, пройти интеграционное ревью.
