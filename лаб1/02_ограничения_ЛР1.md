# Лабораторная работа №1 — Ограничения и запреты

> Источники: методичка (разделы 1.1, 3, 4.4), Семинар 1 слайды 16–17, чеклист качества C4 (Лекция, сл. 29–30). Файл-компаньон: [01_задачи_ЛР1.md](01_задачи_ЛР1.md).

## 1. Содержательные ограничения диаграмм

### L1 — Системный контекст
- Система изображается **единым неделимым «чёрным ящиком»** — никакой внутренней структуры, контейнеров и компонентов на L1 быть не должно.
- **≥ 3 различных пользовательских роли (персоны)** + центральный блок.
- **≥ 3 внешних программных/аппаратных систем**, находящихся вне зоны прямого контроля разработчиков.
- Все связи **строго направленные** (стрелка имеет инициатора и направление движения данных) и обязательно снабжены **текстовым описанием передаваемых данных**.
- Между одной парой элементов допускается несколько стрелок, если они выполняют концептуально разные бизнес-задачи.

### L2 — Контейнеры
- **≥ 5 технологических контейнеров**, и в их числе обязательно: мобильное приложение, веб-приложение, бэкенд-сервисы, хранилища данных.
- Для **каждого** контейнера зафиксирован **конкретный технологический стек** (языки, фреймворки, СУБД) — без стека контейнер считается неполноценным.
- Для **всех** межсервисных связей указан сетевой протокол взаимодействия.
- Типовые протоколы стыков (из семинара): `HTTPS/JSON` — API, `SQL/TCP` (порт 5432) — БД, `MQTT/TCP` (8883) — IoT.

### Общие (из чеклиста C4, лекция сл. 29–30)
- У диаграммы есть заголовок (тип + система) и легенда/ключ (`LAYOUT_WITH_LEGEND()`).
- Тип каждого элемента указан явно (Person/System_Ext/Container/ContainerDb…).
- У каждого элемента — краткое описание назначения.
- На одной диаграмме — не более **7±2 элементов**.
- Метки связей конкретные («отправляет команду бронирования»), не общий «использует».

## 2. Ограничения инструментов

- **Только экосистема PlantUML**: PlantUML + библиотека **C4-PlantUML** (подключение через `!include https://raw.githubusercontent.com/plantuml-stdlib/C4-PlantUML/master/C4_*.puml`; в самой методичке ссылка напечатана без дефиса — это опечатка, без дефиса GitHub отдаёт 404).
- **Запрещено** использовать альтернативы (Structurizr, Mermaid.js, draw.io, Lucidchart) — методичка, раздел 3.2: «все практические задания выполняются строго с использованием экосистемы PlantUML».
- Рекомендуемый локальный стек (раздел 3.2):
  1. **Visual Studio Code** — единая среда для puml-кода;
  2. расширение **PlantUML** для VS Code — подсветка, автодополнение, предпросмотр по `Alt+D`;
  3. **Docker-контейнер PlantUML Server** — локальный рендеринг без отправки кода на публичные серверы (конфиденциальность);
  4. **Graphviz** — движок расчёта раскладки графа (обязателен для сложных диаграмм L2/L3).

## 3. Запреты синтаксиса PlantUML (проверяются CI/CD)

- ❌ **Запрещены макросы жёсткого позиционирования**: `Rel_R`, `Rel_L`, `Rel_D`, `Rel_U` (и вариации `Rel_Down` и т.п.). Направление раскладки должен определять Graphviz сам — иначе конфликт визуализации и падение сборки.
- ✅ Разрешён **только** макрос `Rel(от, кому, 'описание', 'протокол')`.
- ❌ **Запрет локальной стилизации**: любые кастомные цвета, шрифты, `skinparam` выносятся в главный файл проекта. Файлы студентов содержат только чистую логику структуры.
- ❌ Опечатки в ID элементов недопустимы: связи строятся строго по **глоссарию глобальных идентификаторов** (см. раздел 4).
- Пример ошибки из методички: `Rel_D(mobile_app, api_gateway, ...)` → `Error: Macro 'Rel_D' is banned by methodologist guidelines` → сборка падает с ❌.

## 4. Глоссарий идентификаторов

Связи в PlantUML строятся по строгим текстовым ID. Глоссарий из методички (для кейса Smart Parking — **для своей темы нужно завести аналогичные собственные ID и не менять их между диаграммами и работами**):

| ID | Элемент | Тип |
|---|---|---|
| `driver` | Водитель | Пользователь |
| `admin` | Оператор парковки | Пользователь |
| `mobile_app` | Мобильное приложение водителя | Контейнер |
| `admin_web` | Веб-панель администратора | Контейнер |
| `api_gateway` | Бэкенд / API Gateway | Контейнер |
| `database` | Центральная БД PostgreSQL | БД |
| `iot_service` | Сервис интеграции с IoT | Контейнер |
| `payment_gateway` | Внешний платёжный шлюз | Внешняя система |
| `iot_sensors` | Датчики и шлагбаумы | Внешняя система |

Правила по ID: единый глоссарий на всю команду; ID контейнеров/компонентов используются как «стыковочные шлюзы» между зонами ответственности участников; изменение ID согласуется с командой.

## 5. Содержательные запреты по заданию

- ❌ **Нельзя выполнять кейс «Умная парковка»** — он приведён в методичке как сквозной демонстрационный пример и «не подлежит выполнению». Все диаграммы строятся строго по **собственной теме курсового проекта**.
- ❌ Нельзя показывать на L1 внутреннее устройство системы (контейнеры/компоненты) — это ошибка уровня абстракции.
- ❌ Нельзя «всё на одной схеме»: каждый уровень — отдельная диаграмма с отдельным файлом.
- ❌ Нельзя оставлять связи без протокола на L2 (на L1 протокол желателен и в примерах присутствует — HTTPS, REST/HTTPS).

## 6. Организационные ограничения

- Сдача: отчёт размещается в **электронной образовательной среде (ЭОС)**.
- **Индивидуальная защита обязательна**, даже при командной работе: преподаватель проводит личный опрос по всем уровням C4. Каждый студент обязан уметь самостоятельно спроектировать и объяснить локальные версии диаграмм.
- Командная матрица ответственности (методичка, 4.2): Тимлид — глобальная контекстная диаграмма, интеграционное ревью, глобальный техстек; разработчики — индивидуальные L1 (окружение своего контейнера) и L2 (свой узел + обоснование стека).
- Контроль преподавателя через Git: распределение коммитов по авторам, качество Pull Requests и Code Review (для последующих ЛР и интеграции).
- Привязка к дедлайнам курсового проекта (Семинар 1): к 20.10 — спринт 1 + главы 1–2; к 20.11 — главы 3–4 (в них входит архитектура C4). ЛР защищаются в течение семестра.
- Уникальность авторского текста отчёта ≥ 70–80%.

## 7. Чеклист самопроверки перед сдачей

- [ ] На L1 ровно один центральный блок-система, ≥ 3 персоны, ≥ 3 внешние системы?
- [ ] Каждая стрелка направлена и подписана (что передаётся)? На L2 указан протокол?
- [ ] На L2 ≥ 5 контейнеров, у всех указан стек, есть мобильное + веб-приложение, бэкенд, хранилище?
- [ ] Нет ни одного `Rel_R/Rel_L/Rel_D/Rel_U`, только `Rel()`?
- [ ] Нет `skinparam` и кастомных стилей в личных файлах?
- [ ] ID элементов совпадают с глоссарием команды?
- [ ] Диаграммы отрендерены (PNG/SVG), легенда и заголовок на месте?
- [ ] Таблица контейнеров и отчёт собраны и загружены в ЭОС?
