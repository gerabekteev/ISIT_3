## 2. Что такое модель C4 (сл. 8–12)

- **Модель C4** (Context, Container, Component, Code) — подход к визуализации и документированию архитектуры ПО. Автор — британский архитектор **Саймон Браун**, 2006–2011, в основе — идеи UML и модели архитектурного представления «4+1».
- Проблема, которую решает: классические UML-диаграммы и досочные схемы превращаются в «беспорядочное нагромождение прямоугольников и линий»; неоднозначные схемы замедляют команду.
- **Аналогия — картографическая система / «Google Карты»**: сначала вся страна (система), затем город (контейнеры), район (компоненты), здания (код). Последовательная детализация, а не «всё на одной схеме».
- **Базовые принципы C4**:
  1. Иерархический подход — каждый следующий уровень детальнее предыдущего;
  2. Целевая аудитория — разные уровни для разных стейкхолдеров;
  3. Абстракция — каждый уровень скрывает несуществующие на нём детали;
  4. Единая нотация — стандартизированный набор элементов;
  5. Декларативность — диаграммы описывают структуру, а не процессы.
- C4 — **не строгая нотация, а гибкая методика**: не требует конкретного инструмента, даёт структуру повествования. Не обязательно использовать все 4 уровня — часто достаточно контекста и контейнеров.
- Типичная ошибка — попытка уместить всё на одной схеме: она перегружается и становится нечитаемой.

## 3. Основные абстракции C4 (сл. 13–16)

Для уровней 1–3 используется **5 элементов**: пользователи, программные системы, контейнеры, компоненты и отношения.

| Абстракция | Что это | Примеры |
|---|---|---|
| **Лицо (Person)** | Пользователь системы: актор, роль, персона | Водитель, оператор, клиент банка |
| **Программная система (Software System)** | Высший уровень абстракции; то, что представляет ценность для пользователей. Границы системы обычно совпадают с границей ответственности одной команды | Интернет-банкинг, Smart Parking |
| **Контейнер (Container)** | Приложение или хранилище данных, которое должно быть **запущено** для работы системы. **Не путать с Docker-контейнером!** Независимо развертываемая исполняемая сущность | Серверное веб-приложение (Java EE, ASP.NET, Node.js), SPA (JavaScript), мобильное/десктопное приложение, СУБД, файловая система |
| **Компонент (Component)** | Совокупность связанной функциональности за чётко определённым интерфейсом; «набор классов реализации за интерфейсом». Выполняется **в одном процессе с другими компонентами контейнера** | Контроллер, сервис, репозиторий, модуль авторизации |
| **Отношение (Relationship)** | Взаимодействие между элементами | Стрелка с описанием |

Иерархия: **Система → Контейнеры → Компоненты → Код**.

## 4. Четыре уровня моделирования (сл. 17–24)

| Уровень | Название | Аудитория | Фокус / вопрос | Типичные элементы |
|---|---|---|---|---|
| L1 | **Контекст (Context)** | Все стейкхолдеры, включая нетехнических | Какую ценность даёт система и какова её среда | Целевая система, пользователи, внешние системы |
| L2 | **Контейнеры (Containers)** | Техлиды, архитекторы, DevOps | Из каких высокоуровневых технических блоков состоит система | Веб/моб. приложения, API, БД, микросервисы |
| L3 | **Компоненты (Components)** | Разработчики, техспециалисты | Из каких блоков состоит контейнер | Контроллеры, сервисы, репозитории |
| L4 | **Код (Code)** | Разработчики | Как компонент реализован в коде | Классы, интерфейсы, функции |

### L1 — Контекст
Система как единый **«чёрный ящик»** в её естественной среде. Элементы: целевая система (один блок), пользователи, внешние системы, отношения между ними (потоки данных, API-вызовы).
Эталонный пример (интернет-банкинг): *Клиент личного банкинга* —«просматривает балансы и совершает оплаты используя»→ *Система интернет-банкинга* —«отправляет письма используя»→ *E-mail система (Microsoft Exchange)*; —«получает информацию о счете и совершает платежи используя»→ *Банковская система мэйнфрейма*.

### L2 — Контейнеры
«Зум» внутрь системы: контейнеры = самостоятельно выполняемые части (веб- и мобильные приложения, SPA, БД, микросервисы, серверные приложения). **Технологические решения — обязательная часть диаграммы.** Протоколы пишутся на связях: `[JSON/HTTPS]`, `[SQL/TCP]`, `[DMZ/HTTPS]`.
Пример (интернет-банкинг): рамка Internet Banking System [Java Spring] внутри: Веб-приложение [Java/Spring MVC], SPA [JavaScript/Angular], Мобильное приложение [Xamarin], API-приложение [Java/Spring MVC], База данных [Oracle Schema]; снаружи: E-mail система, Банковский мэйнфрейм.

### L3 — Компоненты
Декомпозиция **одного контейнера** на логические модули, соответствующие реальным абстракциям кодовой базы. Примеры компонентов веб-приложения: контроллеры API, сервисы бизнес-логики, репозитории доступа к данным, компоненты платежей, модули аутентификации.
Пример (API-приложение): Контроллер входа, Контроллер сброса пароля, Контроллер сводки по счетам, Компонент безопасности, E-mail компонент, Фасад банковской системы — все в едином адресном пространстве; наружу — только сетевые связи ([SQL/TCP] к БД, [DMZ/HTTPS] к мэйнфрейму).

### L4 — Код
UML-диаграммы классов (или диаграммы модулей для функциональной парадигмы): классы, интерфейсы, методы/свойства, наследование и имплементация, зависимости. Уровень часто опускают — код меняется быстро. Пример: пакет `com.bigbankplc...mainframe` — интерфейс `MainframeBankingSystemFacade`, его реализация `...Impl`, исключения, `GetBalanceRequest/Response`, `BankingSystemConnection`.

## 5. Диаграммы «вне уровней» (сл. 25–27)

- **Диаграмма системного ландшафта** — карта всех программных систем предприятия/отдела с детализацией C4 для интересующих систем. Пример: Enterprise-рамка «Big Bank plc» — банкомат, интернет-банкинг, мэйнфрейм, e-mail + 3 персоны (клиент, поддержка, бэк-офис).
- **Динамическая диаграмма** — как элементы статической модели взаимодействуют **во время выполнения** для сценария использования. Основана на UML-диаграмме взаимодействия (cooperation/collaboration); элементы располагаются свободно, взаимодействия **пронумерованы** в хронологическом порядке. Пример: сценарий входа — 6 нумерованных шагов от SPA до БД и обратно.
- **Диаграмма развертывания** — как экземпляры систем/контейнеров развернуты в инфраструктуре конкретной среды (prod/stage/dev). Пример: узлы Customer's computer (браузер), mobile device (iOS/Android), bigbank-web** x4 (Ubuntu, Tomcat), bigbank-api** x8, bigbank-db01 (Oracle Primary) и bigbank-db02 (Secondary, «Replicates data to»), bigbank-prod001.

## 6. Система обозначений и правила оформления (сл. 28–30)

- C4 не предписывает нотацию: подойдут простые блоки (доска, стикеры) или UML со стереотипами. Модель не требует конкретной формы/цвета/расположения, но рекомендует простые вложенные блоки.
- **Каждый элемент должен включать**: название; тип элемента (Персона/Система/Контейнер/Компонент); технологию (если применимо); краткое описание назначения. Этот текст устраняет двусмысленность.
- Обязательно: **заголовок диаграммы** (тип + область применения) и **ключ/легенда** (формы, цвета, стили линий, границы, сокращения). Обозначения одинаковы на всех уровнях.

### Чеклист качества диаграммы C4 (сл. 30)
1. Заголовок, описывающий тип и область диаграммы.
2. Ключ/условные обозначения.
3. Акронимы объяснены (в ключе).
4. Тип каждого элемента указан явно.
5. У каждого элемента — краткое описание ключевых функций.
6. Для каждого контейнера и компонента указана **технология**.
7. Каждая линия — **однонаправленная** связь с пометкой направления и цели; конкретные метки вместо общего «использует».
8. Отношения между контейнерами (межпроцессное взаимодействие) помечены **технологией/протоколом**.
9. (сл. 43) На одной диаграмме — **не более 7±2 элементов**.

## 7. Преимущества C4 (сл. 31–37)

1. Единый язык коммуникации (технари + бизнес); 2. Масштабируемость представления (зум по аудитории); 3. Сокращение документации; 4. Согласованность с Agile (итеративная детализация); 5. Управление сложностью; 6. Улучшение процесса проектирования (раннее выявление проблем, модульность); 7. Поддержка развития системы (онбординг, аудит техдолга, миграции).

## 9. Методики эффективного применения (сл. 40–46)

1. Итеративное создание: от контекста вглубь, обновлять по мере эволюции.
2. Фокус на бизнес-ценности и ответственности каждого элемента.
3. Согласованность элементов между уровнями (единая терминология).
4. Управление сложностью: ≤ 7±2 элементов на диаграмме, группировка.
5. Интеграция с кодовой базой: генерация из кода, имена диаграмм = имена кода, обновление в CI/CD.
6. Сочетание с другими методиками: sequence-диаграммы для динамики, ADR для фиксации решений, DDD для доменов.
7. Дополнительно: цветовое кодирование, аннотации, версионирование, as-is/to-be представления.

## 10. Интеграция C4 в процессы разработки (сл. 47–51)

- **Жизненный цикл**: анализ (границы системы) → проектирование (контейнеры/компоненты) → разработка (компоненты/код как руководство) → тестирование → поддержка (документация).
- **Agile**: бэклог-рефайнмент, планирование спринта, технический дизайн, демонстрации, ретроспективы.
- **Документация**: хранение диаграмм в Git рядом с кодом (текстовые форматы!), внедрение в Wiki/Confluence, автогенерация, связка с требованиями/тикетами.
- **DevOps**: автотесты соответствия архитектуры (ArchUnit), генерация диаграмм в CI/CD, планирование инфраструктуры по контейнерной диаграмме.
- **Эволюция**: регулярное обновление, версионирование, as-is/to-be, архитектурные обзоры.

## 11. Внедрение и типичные ошибки (сл. 52–53)

Рекомендации: начинать с малого (пилот), обучить команду, назначить ответственных за диаграммы, интегрировать с привычными инструментами, создать шаблоны, собирать обратную связь, фиксировать успехи.
Ошибки: сопротивление изменениям, избыточная детализация, неактуальные диаграммы (лечится автоматизацией / Definition of Done), непоследовательное применение, фокус на инструментах вместо содержания.

## 12. Дополнения из методички (для полноты)

- Аудитория уровней: стейкхолдерам/продактам — Context; DevOps и смежным командам — Container; разработчикам — Component.
- **Гибрид C4 + UML**: L3 может расширяться UML Component Diagram (порты/интерфейсы), L4 — это UML Class Diagram, динамика — UML Sequence Diagram.
- Подход «сначала абстракция»: фокус на границах («что это, на чём работает, как общается»), а не на синтаксисе стрелок UML.
